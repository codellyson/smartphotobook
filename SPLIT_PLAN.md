# SmartPhotobook — three-piece migration plan

The current single Next.js codebase fights itself in a few places (runtime
platform detection, `pageExtensions` hack, API routes vs. static export). This
plan extracts three deploy units, each built with the right tool, and stages
the migration so the product keeps shipping at every step.

## Target shape

```
                        ┌──────────────────────┐
                        │  smartphotobook.com     │   marketing/landing
                        │  (Astro on CF Pages) │   SEO, pricing, OG cards
                        └──────────┬───────────┘
                                   │ link to app + sign-in
                                   ▼
   ┌──────────────────────────┐          ┌──────────────────────────────┐
   │  app.smartphotobook.com     │          │  api.smartphotobook.com         │
   │  (Vite + React SPA       │ ───────► │  (Hono on Cloudflare Workers │
   │   on CF Pages)           │   share  │   + D1 SQLite + R2 + BetterAuth)
   │  + Tauri desktop wrapper │ ◄──────  │   /p public proofing view    │
   │  local-first editor      │   token  │   /shares dashboard          │
   └──────────────────────────┘          └──────────────────────────────┘
```

All three units on Cloudflare. One vendor, one DNS panel, one bill.

Three deployables. The editor talks to the API only when the photographer
opts in (Share with clients). Clients land on `api.smartphotobook.com/p?token=…`
in any browser.

---

## Unit 1 — Editor SPA (`apps/editor`)

**Tech:** Vite + React 18 + TypeScript. Tauri v2 desktop wrapper consumes the
same build.

**Routes (client-side):**

- `/` → projects home
- `/designer` → editor
- `/settings` → metadata + DPI

(no SSR, no server-side metadata — marketing handles SEO)

**Owns:**

- Local album storage (IndexedDB on web, AppData on desktop)
- Photo storage (IndexedDB blobs on web, filesystem paths on desktop)
- All design surfaces (cells, overlays, templates, undo/redo, exports)
- JPEG rendering for both PDF export and proofing uploads

**Does not own:**

- Cloud proofing state
- Marketing site
- Any server-side rendering

**Build:**

- `pnpm --filter editor dev` → Vite dev server
- `pnpm --filter editor build` → `apps/editor/dist/` static bundle
- `pnpm tauri build` → wraps `dist/` into a native installer

No more `TAURI_BUILD=1` env flag. The same build serves both web and desktop;
Tauri just frames it. Runtime detection via `window.__TAURI__` stays for
filesystem branching, but is now isolated to `lib/platform/`.

## Unit 2 — Proofing service (`apps/proofing`)

**Tech:** Hono on Cloudflare Workers. D1 (SQLite-on-edge) for metadata, R2
for JPEGs. [BetterAuth](https://www.better-auth.com) for session + magic-link
auth, using its D1 adapter.

**Endpoints:**

- `POST /api/share/init` — photographer creates a link record →
  returns `{ token, uploads: [{ idx, url }] }` with presigned R2 PUTs
- `POST /api/share/finalize` — photographer confirms uploads succeeded; link
  becomes live
- `GET /p?token=…` — public proofing client view (Worker-served HTML +
  small client-side JS for the carousel + love button)
- `POST /api/reactions?token=…` — client posts love/un-love
- `GET /api/shares` — photographer dashboard data (auth-gated)
- `GET /shares` — photographer dashboard HTML (auth-gated)
- `DELETE /api/shares?token=…` — revoke → also deletes R2 objects
- `/api/auth/*` — BetterAuth-owned routes (sign-up, sign-in, magic-link
  verify, sign-out, session refresh)

**Data model (D1):**

```sql
-- BetterAuth owns these (generated by `pnpm better-auth migrate`):
-- user, session, verification, account

-- App tables:
CREATE TABLE proofing_links (
  token        TEXT PRIMARY KEY,
  user_id      TEXT NOT NULL REFERENCES user(id),
  name         TEXT NOT NULL,
  meta_json    TEXT NOT NULL,
  created_at   INTEGER NOT NULL,
  finalized_at INTEGER,           -- NULL = upload still in progress
  revoked      INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_links_user ON proofing_links(user_id);

CREATE TABLE spread_images (
  link_token   TEXT NOT NULL REFERENCES proofing_links(token),
  idx          INTEGER NOT NULL,
  r2_key       TEXT NOT NULL,     -- "p/<token>/<idx>.jpg"
  PRIMARY KEY (link_token, idx)
);

CREATE TABLE reactions (
  id           TEXT PRIMARY KEY,
  link_token   TEXT NOT NULL REFERENCES proofing_links(token),
  client_name  TEXT NOT NULL,
  spread_id    TEXT NOT NULL,
  loved        INTEGER NOT NULL,
  created_at   INTEGER NOT NULL,
  UNIQUE (link_token, client_name, spread_id)
);
CREATE INDEX idx_reactions_link ON reactions(link_token);
```

**Photo upload — direct to R2, never through the Worker:**

Workers cap request bodies at 100 MB. A 20-spread album at 300 DPI bumps
into that ceiling. Streaming through a Worker also burns CPU time on the
free tier. So uploads bypass the Worker entirely:

1. Editor calls `POST /api/share/init` with album metadata + spread count
2. Worker writes `proofing_links` (with `finalized_at = NULL`) + one
   `spread_images` row per spread, generates a presigned R2 PUT URL per
   spread via the R2 binding, returns `{ token, uploads: [{ idx, url }] }`
3. Editor PUTs each JPEG directly to R2 (Content-Type: `image/jpeg`)
4. Editor calls `POST /api/share/finalize` → Worker sets `finalized_at`
5. A cron-scheduled Worker sweeps un-finalized rows older than 10 min
   and deletes the orphan R2 objects

JPEGs are served from a public R2 bucket attached to a custom subdomain
(`r2.smartphotobook.com`). Revocation requires deleting the R2 objects (cheap)
since the bucket is public; for stricter privacy, route reads through the
Worker with short-lived signed URLs.

**Auth (BetterAuth on D1):**

- BetterAuth's D1 adapter handles user/session/verification tables out of
  the box. No manual SQL for auth.
- Magic-link plugin: photographer enters email → Worker sends a one-time
  link via Resend (Resend has a Workers SDK, stays edge-only). Click →
  session cookie issued.
- Session cookies are httpOnly + Secure + sameSite=Lax, 30 day expiry,
  rolling refresh on activity.
- The editor's pre-split `getPhotographerId()` localStorage UUID becomes a
  legacy migration value — first-sign-in offers "link previous shares to
  this account?" using the old UUID as a one-time claim token.

**Cost ceiling (free tier headroom for early product):**

| Resource | Free tier             | Where 100 albums/day puts you      |
|----------|-----------------------|------------------------------------|
| Workers  | 100k req/day          | ~600 req (well under)              |
| D1       | 5 GB, 5M reads, 100k writes/day | a few hundred writes (under) |
| R2       | 10 GB storage, 1M class A ops/mo, 10M class B ops/mo, **zero egress** | ~10 GB storage = right at the line; bumps to ~$0.015/GB/mo after |

Egress-free R2 is the killer feature for an image-heavy product like this.

**Local dev:**

- `wrangler dev` runs Workers locally with miniflare; D1 + R2 are emulated
  on disk (`.wrangler/state/v3/{d1,r2}/`)
- BetterAuth picks up the D1 binding from `env.DB` regardless of local vs
  prod
- `wrangler d1 migrations apply DB --local` for schema changes
- Resend has a "dev" mode that logs emails to console — wire that for local

**Deploy:**

- `wrangler deploy` for the Worker
- `wrangler d1 migrations apply DB` for schema
- R2 bucket created once via `wrangler r2 bucket create`
- DNS: `api.smartphotobook.com` → Workers route; `r2.smartphotobook.com` →
  public R2 bucket

## Unit 3 — Marketing site (`apps/marketing`)

**Tech:** Astro. Static export, deployed to Cloudflare Pages
(same vendor as the editor + proofing — single dashboard, single DNS panel).

**Routes:**

- `/` — landing
- `/pricing` — eventually
- `/features` — eventually
- `/blog/*` — eventually

**Owns:**

- All public-facing SEO surface
- OG images, sitemap, robots.txt
- Sign-in CTA → links to `api.smartphotobook.com/auth` (magic link flow lives
  in the proofing service since it owns sessions)

**Why Astro:**

- Zero JS by default. Lighthouse scores stay perfect without effort.
- Markdown content (blog posts, docs) is trivial.
- We have no need for React on the marketing surface.

## Cross-cutting decisions

### Shared types

A `packages/contracts` workspace holds the TS interfaces used by both the
editor and the proofing service. The "share an album" payload, the spread
shape sent for rendering, the reaction shape — anything that crosses a
network boundary. Both apps import from `@smartphotobook/contracts`.

### Photographer identity

- Pre-split: UUID in localStorage. Insecure but adequate for demo.
- Post-split: BetterAuth magic-link sessions. The editor talks to
  `api.smartphotobook.com/api/auth/*` for sign-in; BetterAuth's session cookie
  is set on `.smartphotobook.com` so all three subdomains see it.
- Legacy UUIDs become a one-time "claim previous shares" flow on first
  sign-in — the editor sends `{ legacyId }` with the first authenticated
  request and the Worker reassigns those `proofing_links` to the new
  `user_id`.

### Photo data contract

Currently `Photo.src` is overloaded — sometimes a blob URL, sometimes a
`convertFileSrc` path. Pre-split, we make it explicit:

```ts
type PhotoSource =
  | { kind: "blob"; storeId: string }     // resolved via IndexedDB on web
  | { kind: "path"; absolute: string };   // resolved via Tauri convertFileSrc

type Photo = {
  id: string;
  cap: string;
  orient: "L" | "P" | "S";
  source: PhotoSource;
};
```

`src` becomes a render-time getter, not a persisted field. This kills a
whole class of "the URL still works but points at nothing" bugs.

### Domains

- `smartphotobook.com` → marketing (Astro on Cloudflare Pages)
- `app.smartphotobook.com` → editor SPA (Vite build on Cloudflare Pages)
- `api.smartphotobook.com` → proofing service (Hono on Cloudflare Workers)
- `r2.smartphotobook.com` → R2 bucket for public spread JPEGs

Tauri build embeds `app.smartphotobook.com` in its bundle (offline-first; the
host is only used as a CORS allow-list signal).

BetterAuth's session cookie is scoped to `.smartphotobook.com` so the editor at
`app.` can read it while signing in via `api.`

The editor reads `API_BASE_URL` from a build-time constant. Settable per
build (dev, staging, prod). Tauri picks the prod URL by default.

### Cloud URL is no longer build-time-coupled to the API

Today: `NEXT_PUBLIC_CLOUD_URL` is baked in. Bad for desktop self-hosting.

After split: the editor lets the photographer choose an API endpoint in
Settings ("Proofing server"). Default is `api.smartphotobook.com`. A
self-hosting photographer points it at their own. The setting persists with
their user profile (or per-project, if you want even more flexibility).

## Migration phases

Each phase ships a working product. No big-bang rewrites.

### Phase A — in-place cleanup (1 session)

Stay in the current Next.js codebase. Do the three things that hurt most:

1. Split `lib/platform.ts` into `platform.web.ts` and `platform.desktop.ts`,
   re-exported through a build-flag-gated `platform.ts`. Drop the runtime
   `window.__TAURI__` ladder.
2. Move API routes into `app/(server)/api/...` so the server boundary is
   visible in the file tree. (Drop the `pageExtensions: ["tsx"]` hack and
   use a route group exclude instead.)
3. Refactor `Photo` to the discriminated-source shape above. Update the
   renderer + storage to resolve `source` at render time.

**Done when:** the codebase compiles, all 7 phases still work, the platform
file no longer branches at runtime, and `Photo.src` is gone.

### Phase B — extract the proofing service (1–2 sessions)

Stand up `apps/proofing` as a Cloudflare Worker. Concretely:

1. `pnpm create cloudflare apps/proofing --type=hello-world --framework=hono`
2. `wrangler d1 create smartphotobook-proofing` → bind as `DB`
3. `wrangler r2 bucket create smartphotobook-spreads` → bind as `BUCKET`
4. Add BetterAuth with the D1 adapter and magic-link plugin; run the
   initial migration (`pnpm better-auth migrate`)
5. Port the four endpoints from `app/api/*` into Hono routes, swap
   the JSON-file store for D1 queries, swap `public/p-uploads/` for R2
   presigned PUT URLs
6. Move `/p` and `/shares` HTML out of Next.js into the Worker (Hono's
   `c.html()` or a small JSX-on-edge renderer)
7. Wire the editor's API base URL to `http://localhost:8787` (Wrangler
   dev) for local, and the prod Worker URL for production

**Done when:** the Next.js app no longer has any `app/api/*`, `app/p/`,
or `app/shares/` routes. `wrangler dev` boots the Worker locally with
miniflare-backed D1 + R2. The editor (still in the monolith) can run the
share → love → see-in-dashboard roundtrip against it.

### Phase C — extract the editor SPA (1–2 sessions)

Create `apps/editor` as a fresh Vite project. Move `components/`, `lib/`,
the relevant `app/*` page bodies into Vite-compatible routes (likely
`react-router` for `/`, `/designer`, `/settings`). Strip Next.js-specific
imports (`next/link` → `react-router` `Link`, `next/navigation` →
`react-router` hooks).

The Tauri config moves with it. `apps/editor/src-tauri/` replaces the
project-root `src-tauri/`.

**Done when:** `pnpm --filter editor dev` opens the editor, `pnpm tauri:dev`
opens the desktop window, photos persist, share button hits the proofing
service.

### Phase D — extract the marketing site (1 session)

Create `apps/marketing` as an Astro project. Move `app/page.tsx` (the
landing) and `app/globals.css` (the landing portions only) over. Set up
deployment.

DNS: `smartphotobook.com` → marketing, `app.smartphotobook.com` → editor SPA,
`api.smartphotobook.com` → proofing.

**Done when:** all three domains resolve to the right artifact, the landing
links cleanly into the editor, the editor's Share button hits the proofing
API, and clients land on `api.smartphotobook.com/p?token=…` from any browser.

## Open questions

- **Server-rendered HTML for `/p` vs. an SPA?** Worker-rendered HTML +
  minimal vanilla JS for the love button is cheapest; the public viewer
  doesn't need React. The dashboard at `/shares` can stay simple HTML too —
  htmx-style server-rendered actions work fine on Workers.
- **R2 bucket public or proxied?** A public bucket on `r2.smartphotobook.com`
  is dead simple but means revoked tokens leak content (you have to delete
  the R2 objects to actually un-share). A proxied bucket adds a Worker hop
  per JPEG fetch but lets you enforce revocation at request time. Start
  public; add proxying when revocation actually matters.
- **Sessions in D1 vs. KV?** BetterAuth defaults to its primary DB
  (D1 here), and that's fine. KV is faster for read-heavy session lookups
  but eventually consistent. Defer until session reads show up in the
  perf budget.
- **Do photographers ever want to revoke + re-issue a share with the
  same token?** No, generate a fresh token each time. But the dashboard
  should remember client names from prior shares so a "share again with
  the same clients" flow is one click.
- **Self-hosted proofing for power users — Phase D+1?** Worth designing
  the API endpoint config from the start so it's not a retrofit. The
  schema is small enough that a self-hoster could run the same Worker
  on their own Cloudflare account by changing one DNS record.

---

## What we are NOT doing

- Stripe / paywall — Phase D+1 at earliest.
- OAuth / social login — magic link only.
- Native mobile — proofing client is responsive web.
- A different desktop framework — Tauri stays.
- Real-time collaboration on the same album — single-photographer editing,
  shared output. Multi-user editing is a different product.
